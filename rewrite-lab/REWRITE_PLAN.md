# TeleBox 全量模块低资源重写计划

## 目标与范围

- 主体采用 TypeScript + Node.js 24、新插件接口、systemd，采用内存与响应速度均衡策略。
- 重写两个仓库当前全部自有模块。2026-09-05 清单包含 21 个内置入口、127 个主目录扩展入口、3 个历史扩展入口，共 151 个入口；另含核心服务、面板、构建部署和辅助实现。
- 生产的 ai、da、dc、dme、gt、ids、ip、nodeseek、rate、sum、yvlu 优先迁移，其余模块全部纳入交付和验收。
- 保留功能、命令、权限、配置、调度、媒体输出及必要的数据兼容性；全量重写不自动改变安装、启用或规则状态。
- inventory.cjs 为动态盘点入口，记录源码指纹、类别、索引状态及生产优先级。未入索引和 outdated 模块均纳入；外部服务失效等问题逐项登记，不静默省略。
- 第三方依赖、vendored 实现及媒体资源保持来源与许可证，按新架构适配验证，不以自研替代成熟依赖为目标。

## 架构与接口

- 主体提前编译为 JavaScript，生产直接启动产物。插件安装、更新通过短生命周期编译进程完成，不常驻 TypeScript 编译器或 esbuild 服务。
- definePlugin 声明 id、apiVersion、commands、listeners、jobs、settings；PluginContext 提供 signal、Telegram、任务、调度、HTTP、存储、子进程和日志服务。
- 支持单文件 TS 插件及带辅助模块的插件包，提供模板和接口检查。全库统一迁移新接口，TPM 明确拒绝接口版本不兼容的产物。
- 核心集中管理资源与运行代次；清理时限覆盖任务和资源，旧实例未退出时不激活新实例。任务、监听、定时器、连接和子进程显式结束。
- 集中注册 Telegram 更新，按订阅分发；保持原命令授权、别名和监听语义。队列有界、按对话顺序执行，过载明确反馈，已受理任务不静默丢弃。
- 初始业务并发 4、重型媒体并发 1；分页与流式处理大任务，缓存同时限制容量和有效期。普通入口保持轻量，重型 JavaScript 工作由按需子进程执行，初始空闲保温 120 秒。
- Python、ffmpeg、隧道等必要辅助进程统一托管并计入资源开销；保留已验证的渲染和协议能力。
- 第一版沿用 Teleproto 1.229.0、原始 RPC 能力和必要补丁；不同时替换 Telegram 协议库。

## 数据与部署

- 首轮保持 JSON、SQLite、Session 格式及未知字段、任务 ID、游标、大整数精度。需要变更时提供试运行、版本化迁移、校验清单和反向迁移。
- 插件更新按编译校验、旧实例停止、新实例激活执行，失败恢复上一产物；不影响无关插件。
- systemd 托管主进程及其控制组，journald 提供受容量限制的日志保留；适配原有重启、日志导出、更新和版本切换命令。
- 跨重启控制器使用独立 oneshot 服务，不依赖脱离终端来逃离主服务控制组。TeleBox/Next 切换验证目标身份、目标原生插件和数据后执行。
- 保留旧程序、数据及 PM2 部署用于回退；新旧账号实例互斥运行。回退保留切换后新增数据，不直接覆盖为旧快照。

## 实施与交付

1. 固定全量清单、源码版本、依赖与测试数据；逐模块记录命令、监听、调度、配置、权限、外部服务和辅助进程，建立功能及资源基线。
2. 在隔离开发分支实现新启动器、SDK、生命周期、分发、调度、资源预算和存储，交付可运行离线入口。
3. 迁移全部内置能力及生产优先插件，按正常、异常、取消和权限负例对照旧版。
4. 按依赖顺序迁移全库其余模块，包括未入索引和历史入口；每个模块交付新接口实现、配置兼容证据和功能回归，不以仅加包装算完成重写。
5. 完成全库功能矩阵、真实 Telegram 关键链路、视觉输出、故障恢复与迁移回退演练；失效外部依赖保留明确未完成项。
6. 对通过功能验收的完整系统做同机顺序 A/B，选定资源参数后实施授权上线与观察。

每阶段交付可运行产物、测试结果和回退方法。已有跨语言实验保留为参考；主体实现沿已确定的 TypeScript 路线推进。

## 验收标准

- 全量入口与核心服务逐项有证据；生产集合和全库功能负载矩阵分别覆盖。冲突或互斥模块分组，每组新旧版本使用相同模块、配置和数据。
- 连续 50 次重载后无遗留监听器、任务和子进程；24 小时压力运行资源数量有界，稳定期内存无持续增长趋势。
- 同机同负载至少重复 5 次，统计所有必要进程的总 PSS、RSS、峰值、CPU 时间、吞吐、延迟、错误/丢失/重复率及日志服务增量开销。
- 正式稳定空闲总 PSS 比基线下降至少 25%；代表性负载内存峰值不增加；完成相同工作量的 CPU 时间不超过基线 105%，吞吐不低于 95%。瞬时生产快照不替代正式基线。
- 预热本地处理 p95 不超过基线 110%，允许最多 10 ms 测量容差；重型功能冷启动额外等待不超过 2 秒，外部 API 等待单独报告。
- 比较业务并发 2/4/8、重型并发 1/2、保温 0/60/120/300 秒；通过全部约束后选择总 PSS 最低的组合，差异不足 5% 时选择 CPU 更低者。
- 未达标继续优化，不通过缩小功能集合、频繁重启、单纯降低堆上限或遗漏辅助进程宣称达标。
- 账号登录、付费 API、发送/删除/签到、生产切换和提交推送分别在执行前获得明确授权。盘点与离线测试不执行插件初始化或外部业务调用。

## 实施快照

- 两仓库工作分支：`codex/telebox-runtime-v2`。当前启动入口仅支持隔离的 `--check`，尚不是可上线的 Telegram 应用。
- 已实现基础 SDK、生命周期、有界执行队列、JSON/SQLite 存储、HTTP、调度、设置注册、子进程与临时文件管理、Telegram 传输适配、产物校验和版本切换恢复。
- 6 个入口已有新实现和离线回归：内置 help、alias；扩展 gt、ip、ids、dc。AI 文本请求与翻译后端组件已实现，完整 AI 入口和服务注册仍待接通。

- Node 24.19.0：统一 V2 测试 545/545；既有核心回归 61/61、既有扩展回归 23/23；盘点与迁移台账测试 6/6。核心、扩展 V2 与既有核心类型检查通过。
- 提前编译后的离线入口运行成功；gt、ip、ids、dc 候选产物已校验。该结果不证明真实账号链路、全库功能兼容或生产资源收益。
- 下一实施依赖包括账号启动和互斥、旧环境配置映射、必要协议补丁、权限路由、其余内置与扩展、面板、重型工作进程、部署控制器，随后执行完整功能和资源验收。
- 重写分支用于开发与离线验证，生产服务保持原状。当前未执行 24 小时压力运行或同机资源 A/B，最低资源组合尚未确定。
